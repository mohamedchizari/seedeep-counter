# SeeDeep counter

Finds people, vehicles and other everyday things in video and counts them: how many are in the frame each second (the tracked boxes it draws), how many cross a line, how many enter a zone and for how long. Two programs share one detector and one set of tracking rules:

- **`web/`**, in the browser: a camera or a video file, a line at any angle, a zone. Nothing you show it leaves the page. `web/js/seedeep.js` holds all of its logic; `web/index.html` and `web/style.css` are a plain page to run it in.
- **`counter/`**, in Python, offline: a video file goes in; per-second and per-minute counts (CSV), every line crossing (CSV), a summary (JSON and PDF) and the video with the boxes drawn come out.

## Run it

```sh
./fetch_assets.sh                 # downloads the model and the MediaPipe runtime (27 MB), checked by SHA-256

# in the browser
python3 web/serve.py              # then open http://127.0.0.1:8000/

# offline, on a video file
python3 -m venv .venv && . .venv/bin/activate      # Python 3.9 to 3.12; macOS 13+ on Apple silicon, Linux x86_64 (glibc 2.28+), or Windows x86_64 (there .venv\Scripts\activate; not tried); see counter/requirements.txt
pip install -r counter/requirements.txt
python counter/count_video.py web/assets/sample_crosswalk_960.mp4 out/ --line 0.62 --line-text "the crosswalk"

# the tests of the Python tracker (standard library only)
python3 -m unittest discover -s tests -v
python3 tests/mutate.py           # changes the tracker rules listed in it, one at a time, and checks a test fails each time

# a check of the browser page: 19 checks, one to a few minutes with a hardware GPU; with software WebGL only, checks can time out and fail (Node 18+, npm install playwright-core, and Google Chrome:
# Playwright's own Chromium does not play the H.264 sample; `tests/web_check.mjs`'s header lists its settings). It first checks that the page it is
# given serves this repository's web/js/seedeep.js, so a server that already held the port is not checked by mistake.
python3 web/serve.py &
CHROME="/path/to/Google Chrome" node tests/web_check.mjs
```

`count_video.py` options: `--line` (the line's height as a fraction of the frame, 0 for none: then `crossings.csv` holds only its header, the crossing columns of `counts_per_minute.csv` are empty, and the PDF and `README.txt` leave the crossings out), `--every N` (look at every Nth frame), `--max-minutes`, `--title` (printed on the summary), `--line-text`, `--model`, `--ffmpeg` (the name or path of the ffmpeg that re-encodes the annotated video to H.264, `ffmpeg` by default; if none is found or it fails, the video stays MPEG-4 Part 2; `''` skips it), `--no-video`. It writes into a work folder inside the output folder (`.seedeep-counter-work`). Once the tables, `summary.json` and `summary.pdf` are written, it moves them into place and deletes an earlier run's video and `README.txt`; then it re-encodes the video it drew while reading (or keeps it as MPEG-4 Part 2), and moves it and `README.txt` into place last. A Ctrl-C, SIGTERM or SIGHUP during the imports ends the run before anything is written (a Ctrl-C that a library swallows or turns into another error there is noted, and ends the run when the imports are done or at that error; the library may print its own message or a traceback first); once the run has started, one while files are being moved takes effect when the move is done, and at any other time it ends the run, and an ffmpeg the run started with it (when `--ffmpeg` is a wrapper script, what the wrapper started ends only when the stop reaches the whole process group, as a Ctrl-C in the terminal does). A SIGKILL of the run's own process ends the run alone and leaves a running ffmpeg running until it ends; one sent to its process group (kill -9 of the shell's job, say) ends the ffmpeg too. Outside Windows, SIGTERM and SIGHUP end the run by that signal, as Ctrl-C does. A Ctrl-C in Python's own start-up, before the script has set up its handling, can end in a traceback. A signal ignored when the run starts stays ignored: under `nohup`, a closed terminal does not stop the run. The folder's mark, a file named `.seedeep-counter-output`, lists the files this program put there with their sizes and modified times; a later run replaces or deletes only those, and only while their size and modified time are unchanged (one that changes during a run is left as it is, before or after this run's file of that name was moved in, and the run ends with exit code 4; if it changed before, that run's file is not kept). The work folder holds a file naming this program (`made-by-count_video.txt`). At the start of a run, it deletes a work folder left there only when that file is in it or the folder is empty; at the end, it deletes the work folder it made; either way it deletes that file last. Outside Windows the work folder is made readable and writable by its owner only, so another user cannot put a file or a link in it; the run opens it without following a link and writes, moves and deletes the tables, `summary.json`, `summary.pdf`, the mark and `README.txt` through the folder itself, so a link put in the folder's place, or in it under one of those names, is not followed. OpenCV writes the raw video by its path, just after a check that the folder is still the one the run made, and ffmpeg, run inside the folder, writes `annotated.mp4` there by name: a link put in their place during a run (outside Windows, by the same user) is followed. When the run finds a link, or anything but a plain file, under a name it uses in the work folder (it looks before it writes each file and before each move, and after OpenCV and ffmpeg are done), it stops with a message (exit code 2) and moves nothing more; a link is never moved into the output folder. If the work folder is replaced during a run (by a link, say), the run stops with a message (exit code 2) and writes and deletes nothing more there. A folder holding a file under one of the output names that the mark does not list, or that has changed since, is refused (a folder marked by an earlier version, whose mark lists no files, too); so is a folder whose `.seedeep-counter-work` is a link or cannot be read, or holds files but not that file as a plain file (an earlier version's, say, or a `made-by-count_video.txt` that is a link), an input, model or ffmpeg inside the work folder, an input that is itself one of the output files, an input that is not a regular file (a folder, a FIFO, a device, or a pipe such as `/dev/stdin` fed by another program: OpenCV would wait on a FIFO with no writer past any stop, so every FIFO is refused, also one being written into), a mark that cannot be read, an output folder that cannot be written or searched or that is inside a `.seedeep-counter-work` folder, and an output name or the mark that is a folder or a link. OUT_DIR is taken as its resolved path (links and `..` resolved; `x/../y` makes `y`, not `x`), and the run's messages name it so. A run locks the output folder before it looks into it and holds the lock until it ends, so a second run into it meanwhile is refused (where Python has `fcntl`, so not on Windows, and not on a disk that cannot lock, where the run says so and goes on). Each time files are moved into place, the new mark is written first, in the work folder, and moved in last, so a failure while it is written (a full disk, say) moves nothing. The outputs are made with the permissions the umask allows, as a file the shell makes would be. A run that fails or is stopped before its tables are moved leaves an earlier run's outputs as they were; one stopped during the video step leaves its tables, summary and PDF in place without the video and `README.txt`. What a stopped run leaves in the work folder, such as the partial video, stays there until the next run into that folder deletes it. A work folder that could not be deleted at the end of a run (it cannot be listed, or a file in it cannot be deleted or keeps coming back) stays too, and the run says so; the next run tries again and, if it still cannot delete it, ends with a message (exit code 2). A run that could read no frame deletes the output folder again, with the folders above it that the run made, each only if nothing else is in it, when its work folder could be deleted (when not, it says so). The `ffmpeg` message says when the H.264 video was not made, with what ffmpeg said; an ffmpeg that fails or runs out of time does not cost the tables. ffmpeg runs inside the work folder, with its messages going to a file there and nothing on the run's own output, so a pipe from the run (`count_video.py ... | tail`) ends when the run does; a `--ffmpeg` wrapper script should name the programs it starts by their full path, and an FFREPORT log written in the work folder is deleted with it. An ffmpeg still running after ten times the video's length (at least five minutes) is stopped (a wrapper script, not what it started), and the video stays MPEG-4 Part 2. It reads to the end of the file or to `--max-minutes` (default 60), whichever comes first, and exits with an error if it could read no frame.

The browser page needs the files to come from a server, not from `file://`, and at the root of the host: the page asks for `/style.css`, `/js/`, `/vendor/`, `/models/` and `/assets/`, so a sub-path (such as a project page on GitHub Pages) breaks it. `web/serve.py` sends `.mjs` and `.wasm` with the content types the browser requires. If the page stays on its loading message or says the detector could not load, the runtime or the model is usually missing: run `fetch_assets.sh`. The message names the missing file when it is `vision_bundle.mjs`, the model or the WebAssembly loader `vision_wasm_internal.js`; when it is the `.wasm` file itself, it says that fetching the wasm failed (each tried by hand, once, with the file answering 404). When the browser gives no WebGL on the kind of canvas the detector draws on, the message says so instead, and that the page needs WebGL. That message comes back whenever the page has nothing else to say, also after "Sample clip" is pressed.

## Method

**Detector.** EfficientDet-Lite0 (float16) as published by MediaPipe, run by MediaPipe Tasks Vision 0.10.21 in the browser (GPU delegate, falling back to CPU; MediaPipe reads the video frames through WebGL either way, on a canvas it makes for that: an OffscreenCanvas where there is one, except in Safari before 17; a browser with no WebGL on that kind of canvas cannot look at a frame, and the page checks it when it loads and says so) and by MediaPipe for Python offline. It knows the 80 classes of the COCO dataset. Settings: score threshold 0.4, at most 25 detections a frame.

**Groups.** `person`; vehicles are `car`, `truck`, `bus`, `motorcycle`, `bicycle` and `train`; everything else is "other".

**Tracker** (`counter/tracker.py`; the same rules in `web/js/seedeep.js`). A track's *hits* are the frame that started it plus every frame it was matched in since.
- a detection joins a track of the same class if their intersection over union is above 0.3; pairs are taken greedily, best overlap first and equal overlaps to the earlier track, so a detection can end up with its second-best track;
- a track counts as "seen" when it reaches 3 hits;
- a track is dropped after more than 12 frames in a row without a match (frames looked at: with `--every N` that spans 12 × N video frames, and in the browser it counts the frames it kept up with);
- boxes are drawn for tracks matched in the current frame that have at least 2 hits; "in frame" counts these.

**Line.** Crossings are counted for people and vehicles only, from a track's third hit on, when the centre of its box changes side between two matched frames.
- Browser: the line is a segment you drag, at any angle; a crossing counts only where the centre's new position is level with the segment (its projection falls between the two ends). "Down" is one side and "up" the other. Moving the line does not by itself count a crossing (both positions of a centre are judged against the line as it is now); each move leaves a "line moved" event (a press that moves nothing leaves none).
- Python: the line is horizontal and spans the frame; "down" means towards the bottom of the frame.

**Zone** (browser only): a polygon you drag. A track inside it from its third hit on is "in the zone"; the page counts entries and the mean stay, the stay of a track still inside counted up to the current moment (also while the detector has briefly lost it, until it is dropped) and that of a dropped track up to when it was last seen, where it gets a "left" event. Adding a new zone starts its figures again and leaves a "zone changed" line among the events. Entries and stays are per track, so a track that breaks shows as several short visits (see Limits). Every event in the CSV carries its pass. Removing a zone gives the tracks inside it a "left" event and keeps its figures in the CSV as an earlier zone; moving a corner leaves a "zone moved" event.

**Passes** (browser): when the sample clip loops (or the video's time otherwise jumps back; the page itself has no seek control), a new pass starts: the tracks start again, a track in the zone gets a "left" event where it was last seen, and the per-second rows start again under the next pass number. The totals seen, the crossings and the zone figures carry on across passes.

**Outputs.** The browser's CSV has a row for each second of video in which it looked at a frame, per pass (the most people, vehicles, other things and zone occupants in frame, the frames looked at, the pass), then the totals seen by class, the crossings, the figures of the zone and of any earlier zones, the line and zone as they were when the CSV was made, every event, the source, the detector and the time it was made. The Python counter writes `counts_per_second.csv`, `counts_per_minute.csv`, `seen_by_class.csv`, `crossings.csv`, `summary.json`, `summary.pdf`, `annotated.mp4` (unless `--no-video`) and a `README.txt` describing the files this run wrote; the times it writes in its files are in UTC (summary.pdf's own file metadata dates, set by ReportLab, carry the machine's local time and offset).

## Limits

- **Accuracy has not been measured** on any labelled footage, by us. The annotated video is there so a person can check the counts.
- **"Seen" counts tracks, not people.** A thing the detector loses for more than 12 of the frames looked at and finds again is counted again; two things close together can be seen as one, and two that pass each other can swap tracks. On a busy scene the "seen" total can run far above the most in frame at once (132 against 9 in the run below), and in the browser a person crossing a zone can count as several entries with short stays: with the default zone on the sample clip, the mean stay the page showed stayed under a second on one fast machine; on a slow device (software graphics) it reached several seconds (5.5 and 12.1 s at most in two runs).
- The detector can miss things that are small, far away or partly hidden, and can give a thing the wrong class.
- **The browser counts only the frames it keeps up with.** It looks at each frame the video shows at most once (where the browser has `requestVideoFrameCallback`; elsewhere it looks whenever the video's clock moves, which can be the same frame twice), and a slower device skips frames, so the same video can give different counts on different devices. The Python counter looks at every frame up to `--max-minutes` (or one in every N with `--every`).
- Times in the Python outputs come from the frame rate the file states; a raw stream that states none (a bare `.h264`, say) is timed at whatever rate OpenCV reports for it, or 25 frames a second when it reports none (25 in the one case tried: a raw stream cut from the sample clip, which runs at 24 frames a second), so its seconds can be off.
- The browser line (a segment at any angle) and the Python line (horizontal, full width) are different rules, so their crossing counts on the same video can differ.
- A crossing is counted each time a centre changes side, with no margin: a thing standing on the line whose box shifts by a pixel or two can count crossings in both directions, in both programs.
- If something fails while the page looks at a frame (a lost graphics context, say), it says so on the video, logs the first error of each run of failed frames in the browser's console and tries again on the next frame; the message goes when a frame succeeds. With the video paused, a redraw that fails after the line or the zone is switched is not tried again until the next change; during a drag it is tried on every frame.
- **The browser can stay on a slow GPU.** The page takes the GPU delegate whenever MediaPipe can make one and does not move to the CPU when that is slow. In the one case tried by hand (headless Chrome made to use software WebGL, SwiftShader, on an Apple M1 Pro), it took the GPU delegate and made far fewer detections a second than with the Mac's own GPU.
- The PDF uses the standard Latin fonts, so a `--title`, `--line-text` or input file name in another script shows as boxes there; `summary.json` keeps it as written (UTF-8).
- `counter/` needs mediapipe 0.10.32, which has wheels only for macOS on Apple silicon, Linux x86_64 with glibc 2.28 or later and Windows x86_64, and no source package, so it does not install on an Intel Mac, Linux on ARM or Windows on ARM. OpenCV 5.0.0.93's wheel for Apple silicon needs macOS 13 or later, and numpy 2.0.2 has wheels for Python 3.9 to 3.12 only: below macOS 13, or on Python 3.13 and later, pip tries a long build from source instead. The counter was run on macOS and Linux, not on Windows (where the venv is activated with `.venv\Scripts\activate`).
- It does not read faces, plates or text, and it does not know who anyone is: a track is a box that moved, nothing more.

## One run, one machine

The sample clip (`web/assets/sample_crosswalk_960.mp4`, 24.04 seconds, 960 by 540, 24 frames a second, 577 frames) with the command under "Run it", on an Apple M1 Pro (CPU, the versions in `counter/requirements.txt`):

| | |
|---|---|
| frames looked at | 577 |
| time per detection, mean | 38.6 ms |
| person tracks seen | 132 |
| vehicle tracks seen | 26 |
| line at 0.62: people down / up | 11 / 11 |
| line at 0.62: vehicles down / up | 0 / 3 |
| most people in frame at once | 9 (second 9) |

These are the counter's outputs, not checked against a person's count of the clip. The run gave 132 person tracks while it never showed more than 9 people in frame at once; how many distinct people appear in the clip was not counted, so how many of those tracks are one person's track broken and started again is not known. That is why "seen" is a count of tracks, not of people. The time per detection depends on the machine, and the counts can differ by a few on another machine (one run on Linux x86_64 with mediapipe 0.10.32, OpenCV 5.0.0 and Python 3.13 gave 131 person and 27 vehicle tracks, people 13 / 13, vehicles 0 / 3, at most 10 people in frame; so did one with the versions in `counter/requirements.txt` on Python 3.9). mediapipe 1.1.1 gave the same counts as 0.10.32 on each machine.

## Privacy

The browser page loads the model, the runtime, the sample clip and any settings file from its own server (the browser may keep them in its cache). The camera and any opened file stay in the page; the counts are made into a file in the page. The page's Content-Security-Policy tells the browser to refuse scripts and requests to any other host. The line and zone you set are kept in the browser's local storage, under a key named for the page's path. "Copy these numbers" puts the speed figures, the delegate (GPU or CPU), the time and the browser's user-agent string on the clipboard, nothing else, and only when you press it. `count_video.py` makes no network request of its own, and a run on a video file needs no network (OpenCV fetches an IN given as a URL). Some MediaPipe versions do make one: in a test on Linux x86_64 through a local proxy, mediapipe 1.1.1 connected to play.googleapis.com, Google's logging endpoint, when the detector was closed, on every run that made one (a refused run too), and MediaPipe's maintainers have said they will add no official switch to turn that off (google-ai-edge/mediapipe issue 6291). mediapipe 0.10.32, the version `counter/requirements.txt` pins for that reason, made no connection in the same test, and no network call in a trace of its system calls. The endpoint's address, play.googleapis.com/log, is in the library of mediapipe 1.1.1 for macOS, Linux and Windows, and in none of 0.10.32's (macOS, Linux, Windows). The connection test was one test on one platform; to be sure of a run, make it on a machine with no network.

## Settings and the test hook

A page can set the counter up from a file: `<body data-config="./config.json">`, where the JSON may hold `line` (a height fraction, or `{x1, y1, x2, y2}` in fractions of the frame), `zone` (3 or more points `{x, y}`; the first 8 are used), `classes` (the class names to count; others are ignored) and `start` (`"camera"` or `"sample"`). `web/index.html` has none. The file is used whole or not at all: if it cannot be fetched within 10 seconds, is not a JSON object, or has a field of the wrong shape (a `line` that is neither of the two, a `zone` of fewer than 3 points or with one of its first 8 points not `{x, y}` in numbers, `classes` that is not a list of names, a `start` that is neither), the page says so, shows that message whenever it has nothing else to say, and counts without it. A line kept in local storage is used only when its values are numbers, and a stored zone (3 or more points, cut to 8) only together with it; the values are clamped to the frame; anything else there is ignored. The script also keeps its state in `window.__seedeep` (among others: ready, frames, fps, infMs, delegate, line, zone) for tests such as `tests/web_check.mjs`.
